That is the distance between first and second place across a collection of 94 kernels.

At this margin, the system around the model matters at the level of individual trials. A single failed workload, an unstable measurement, or a B200 hour spent repeating a dead idea can change the collection score.

Databricks disclosed a compact stack: KDA supplies the kernel workflow; Humanize runs the iterative implementation and review protocol; Omnigent coordinates harnesses; Claude implements; Codex reviews. The team gave these agents enough structure to work autonomously for long stretches.

This field note turns that disclosure into an Islo system design. It separates capabilities already available from the small amount of integration work still required. It also defines the evidence the first campaign should return.

01 / PUBLIC SIGNALS

Four systems, four pieces of the machine

The public SOL-ExecBench work already isolates the capabilities a serious kernel campaign needs. The numbers below come from different dates, evaluation stacks, and metric slices. Each result should be read within its original experiment.

A

Cursor

Fleet search

A planner distributed and rebalanced 235 problems across autonomous workers on 27 B200 GPUs. The run lasted three weeks and reported a 1.38× geomean speedup over its baseline.

Keep the worker contract small. Rebalance compute using live performance evidence.

B

doubleAI

Adversarial verification

WarpSpeed reported beating optimized baselines on 90% of 235 problems at 2.24× geomean speedup after one day of search. Its follow-up exposed kernels that passed fixed tests while failing on fresh seeds, unseen shapes, and realistic token distributions.

The verifier controls the meaning of every speedup. Hidden distributions belong in the evaluator.

C

Recursive

Cross-task memory

Many research threads ran jointly across all 235 kernels, retaining useful context and combining promising branches. Recursive reported a mean SOL score of 0.754 across the full benchmark.

Verified techniques should travel between related tasks while candidate code stays isolated.

D

Databricks

Durable writer–reviewer loop

KDA, Humanize, and Omnigent combined Claude implementation with independent Codex review. The current public L1 leaderboard shows Databricks first at 0.751491.

Long-horizon work benefits from explicit roles, state on disk, and a review gate that can reject completion.

RESEARCH HYGIENE

ac4k and Amir M. Mir / SF Tensor also sit near the top of L1. Their leaderboard positions are public; their internal architectures are not. This design does not infer systems from names or scores.

02 / INVENTORY

The infrastructure is mostly here

Islo already exposes the execution primitives behind the loop. The first version needs a B200 evaluator adapter and a campaign scheduler; the agent runtime itself can be assembled from current capabilities.

CURRENT

Persistent isolated computers

One microVM per kernel preserves repositories, compiler caches, Humanize state, failed attempts, and profiler artifacts across disconnects.

CURRENT

Claude and Codex harnesses

Both agents run natively. Omnigent can sit above them for shared sessions, harness switching, monitoring, and human intervention.

CURRENT

Durable parameterized jobs

Jobs provide versioned manifests, typed parameters, timeouts, concurrency, lifecycle policies, logs, and repeatable execution.

CURRENT

Snapshots

Every experiment can start from the same pinned KDA, Humanize, Omnigent, toolchain, dataset, prompt, and playbook version.

CURRENT

Scoped gateways

Host, path, method, response filter, rate, and credential rules give the sandbox access to model APIs and the evaluator without exposing secrets.

CURRENT

Audit and replay

Agent sessions and commands remain inspectable. Candidate manifests connect model activity to evaluator evidence.

ADD

B200 evaluator adapter

The public Islo resource schema currently exposes CPU, memory, disk, snapshots, and lifecycle. A narrow API connects the labs to an external or BYOC B200 pool.

ADD

Campaign scheduler

A small service ranks queued experiments by expected collection-score gain per B200 minute and enforces campaign budgets.

03 / SYSTEM DESIGN

The CPU side thinks. The B200 side decides.

The evaluator is a trust boundary. Agents can design any candidate within the task contract. Only the evaluator can issue a result eligible for promotion.

04 / INNER LOOP

The life of one candidate

Each round leaves enough state for another engineer—or another model—to reconstruct the decision.

  1. 01
    Classify the bottleneck

    Memory traffic, tensor-core utilization, occupancy, reduction structure, launch latency, or fusion headroom.

    analysis.md
  2. 02
    State one hypothesis

    The expected mechanism, affected workload buckets, and the profiler signal that would support it.

    hypothesis.json
  3. 03
    Implement a focused candidate

    Source, compiler flags, parent candidate, task contract, and environment version become its identity.

    candidate.sha
  4. 04
    Run correctness first

    All public and hidden workloads, fresh seeds, numerical checks, fallback coverage, and output sanity.

    verdict.json
  5. 05
    Measure reproducibly

    Warmups, repeated trials, cache clearing, locked clocks, identical ABI, and measurement variance.

    benchmark.json
  6. 06
    Review the claim

    Codex checks scope, evidence, specialization, physical plausibility, and overlap with failed ideas.

    review.md
  7. 07
    Promote, branch, or stop

    The scheduler considers score gain, B200 cost, remaining headroom, and the next defensible experiment.

05 / VERIFICATION

The evaluator defines what “fast” means

doubleAI’s public analysis is the clearest warning in the benchmark. A kernel can satisfy a fixed verifier and still corrupt the workload it was built to accelerate.

One published embedding-gradient kernel accumulated repeated updates directly in BF16. Uniformly sampled token IDs rarely collided, so the verifier accepted the result. Natural text follows a heavy-tailed distribution; frequent tokens collide hundreds of times and expose accumulated rounding bias. Training diverged under one optimizer while another optimizer masked the error.

The B200 evaluator should therefore maintain two contracts:

PUBLIC CONTRACT

Fast local feedback

  • Published shapes and tolerances
  • Deterministic smoke tests
  • Compiler and launch diagnostics
  • Coarse benchmark signal
HIDDEN CONTRACT

Promotion evidence

  • Fresh RNG seeds and held-out shapes
  • Realistic heavy-tailed distributions
  • Accumulator-precision stress cases
  • Fallback and adjacent-shape checks
  • End-to-end workload spot checks

The agent can inspect failures and iterate. It cannot inspect hidden inputs, alter evaluator code, select favorable trials, or publish its own score. Each promotion receipt includes the evaluator version and content hash so a later campaign can reproduce the verdict.

06 / SCHEDULING

Spend B200 minutes where they move the collection

Agent computers can remain highly parallel. GPU evaluation is the scarce serializing resource, so the queue needs an explicit objective.

priority = expected Δ collection SOLexpected B200 minutes

Coverage comes first. A failed kernel contributes zero to the collection average; even a baseline-level correct kernel contributes roughly 0.5. Once every task has a defensible candidate, the scheduler shifts toward measured marginal gain.

A kernel near its analytical bound may justify one carefully targeted experiment. A kernel with large headroom and a clear NCU signal may justify ten. A kernel whose last five distinct hypotheses produced noise should pause and release its budget.

07 / OUTER LOOP

Let evidence teach the next lab

The inner loop improves a kernel. The outer loop improves the search policy used by future labs.

Completed tasks emit small, structured lessons: which tiling family worked, which NCU signal predicted the gain, where numerical stability failed, which shape bucket needed specialization, and which fallback preserved generality.

VERIFIED LESSON normalization / B200 / BF16
Observation
A second HBM pass dominated medium contiguous rows.
Successful move
Fuse variance reduction and affine application; vectorize 16-byte stores.
Failure boundary
Persistent blocks regressed rows below 2K elements.
Evidence
3 replicated benchmarks + DRAM and memory-pipe NCU counters.
Applies when
BF16, contiguous rows, 2K–16K elements, exact accumulation contract.

A curator proposes a new playbook from these lessons. Promotion requires an A/B campaign from identical Islo snapshots on held-out kernels, with equal model and GPU budgets. A stronger playbook must improve correctness, collection SOL, or cost efficiency without increasing verifier failures.

08 / FIRST CAMPAIGN

Eight kernels are enough to prove the system

The first run should validate autonomy, evidence quality, and transfer before spending a full 94-kernel budget.

TASK SET

8 L1 kernels

  • 2 elementwise / vectorized
  • 2 reduction / normalization
  • 2 projection / GEMM
  • 2 backward operations
CONFIGURATIONS

3 controlled runs

  1. KDA + Claude
  2. KDA + Humanize + Codex review
  3. Same loop + verified cross-kernel memory
SCORECARD

7 measured outputs

  • Final SOL score
  • Correct candidates / 100 attempts
  • B200 minutes / promoted gain
  • Human interventions / kernel
  • Repeated failed directions
  • Reviewer-caused corrections
  • Transfer from playbook memory

What the campaign returns

01An Islo KDA snapshot

Pinned tools, harnesses, prompts, task contract, and evaluator client.

02A durable job

One parameterized manifest that can launch, resume, and budget any kernel lab.

03A B200 evidence API

Content-addressed candidates, hidden verification, reproducible timing, and signed receipts.

04A campaign ledger

Every hypothesis, failure, review, benchmark, promotion, and lineage edge.

05A measured harness comparison

Evidence for the value of independent review and shared memory under equal budgets.

06A go / no-go decision

A defensible basis for expanding from eight labs to the complete L1 collection.

THE BUILD

One persistent lab per kernel.
One trusted B200 verdict per candidate.
One playbook that earns every upgrade.

Islo already has the computers, jobs, snapshots, gateways, harness access, and audit trail. The first implementation adds the evaluator adapter and the campaign scheduler, then measures the complete loop on eight kernels.
